Trước hết trả lời một câu:刷题 LeetCode là刷 thẳng trên web tốt hơn hay trên IDE local tốt hơn?

Nếu là dạng chấm thi kiểu Niuke tự xử input/output thì nhất định phải viết trên IDE, cái này không có gì để nói, nhưng **với dạng chấm như LeetCode, cá nhân tôi thích刷 thẳng trên web**, vì hai lý do:

**1, Tiện**

Vì có cấu trúc dữ liệu LeetCode tự định, ví dụ `TreeNode`, `ListNode`, ở local bạn còn phải copy class đó qua.

Mà trên IDE không test được, viết code xong còn phải paste lên web chạy test, vậy thà viết thẳng trên web.

Thuật toán又 không phải code工程, lượng đều比较小, lợi ích autocomplete của IDE cơ bản có thể bỏ qua.

**2, Thực dụng**

Tới lúc phỏng vấn, đề thuật toán interviewer cho đa số mong bạn hoàn thành thẳng trên web, tốt nhất vừa viết vừa giảng思路.

Nếu lúc luyện bình thường đã quen không có autocomplete, quen viết tay code não biên dịch, thì lúc phỏng vấn viết code就能 nhanh và thong dong hơn.

Trước tôi面 Kuaishou, có interviewer bắt tôi [implement thuật toán LRU](https://labuladong.online/algo/data-structure/lru-cache/), tôi viết thẳng implement doubly-linked-list, hash-linked-list trên web hết, mà một lần chạy không bug, thấy được vẻ惊讶 của interviewer 😂

Tôi秋招能 làm máy gặt offer,很大程度 chính vì ải viết tay thuật toán vượt kỳ vọng interviewer,其实 đều vì trước刷题 trên web luyện ra.

Đương nhiên, thực sự không muốn刷 trên web, cũng có thể dùng plugin刷题 vscode hay JetBrains của tôi, plugin và nội dung web của tôi đều融合 hoàn hảo.

Tiếp theo giới thiệu vài cách 「投机取巧」 rất thực dụng và技巧 debug, nâng toàn diện xác suất bạn qua笔试.






## Tránh mạnh đánh yếu

Mọi người cũng biết, phần lớn đề笔试 cần bạn tự xử dữ liệu input, rồi để chương trình in output. Nguyên lý底层 chấm là, dùng redirect `>` của Linux ghi output chương trình bạn vào file, rồi so output bạn với đáp án đúng có giống không.

Vậy难点 của có vấn đề就形同虚设, ta có thể偷工减料, lấy ví dụ đơn giản hóa, giả sử đề nói cho bạn input một串 ký tự cách bằng空格, bảo bạn đây là một linked list đơn, hãy đảo linked list này, mà nhấn mạnh, nhất định phải biến số input thành linked list rồi mới đảo nhé!

Vậy bạn làm sao? Thật就 tự định nghĩa class node `ListNode`, rồi viết code biến input thành linked list, rồi dùng thao tác con trỏ让人头晕老老实实 đảo linked list?

搞 rõ ta tới để AC đề, không phải tới học tư duy thuật toán, hệ chấm không判断 được logic thuật toán, chỉ判断 output bạn có đúng không. Nên cách取巧 là存 thẳng input vào mảng, rồi dùng [技巧 hai con trỏ](https://labuladong.online/algo/essential-technique/array-two-pointers-summary/) vài dòng code đảo nó, rồi in ra xong.

Tôi就见过 không ít đề này, ví dụ đề nói input là một linked list đơn, bắt tôi đảo nhóm linked list, mà còn nhấn mạnh phải dùng đệ quy implement, chính là thuật toán [đảo linked list theo nhóm k](https://labuladong.online/algo/data-structure/reverse-linked-list-recursion/) ở bài trước. Ừ, nếu dùng mảng đảo, hai phút là viết xong, hehe.
 
Còn đề [làm phẳng nested list](https://labuladong.online/algo/data-structure/flatten-nested-list-iterator/) bài trước讲,思路 rất巧, nhưng khi gặp ở笔试, input là một chuỗi dạng `[1,[4,[6]]]`, vậy dùng thẳng regex抽 số ra, chính là một list làm phẳng rồi……






## Chọn ngôn ngữ lập trình

Chỉ xét góc làm bài thuật toán, cá nhân tôi比较建议 dùng Java làm ngôn ngữ笔试. Vì IntelliJ nhà JetBrain实在太香, so editor ngôn ngữ khác, không chỉ có lệnh tắt `psvm` và `sout` (bạn mà连 cái này都不 biết, mau úp mặt đi), mà còn giúp bạn check nhiều lỗi笔误, ví dụ quên tăng biến trong vòng `while`, hay câu `return` viết nhầm vào vòng lặp do疏忽.

C++ cũng還行, nhưng tôi thấy không好用 bằng Java. Tôi nhớ C++连 hàm `split` tách chuỗi cũng không có,光 điểm này tôi đã không muốn dùng C++……

Còn một điểm, code C++ giới hạn thời gian cao, ngôn ngữ khác giới hạn 4000ms, C++ giới hạn 2000ms, tôi thấy挺吃亏. Chả trách xem người ta dùng C++ viết thuật toán, để tăng tốc, đều không dùng container `vector` chuẩn,偏要用 mảng `int[]` gốc, tôi nhìn都頭疼.

Python thì tôi刷题 dùng比较少, vì tôi không thích dùng ngôn ngữ động,不好 debug. Nhưng ngôn ngữ này确实 cung cấp nhiều chức năng thực dụng, nếu bạn深谙套路 Python, có thể投机取巧 lúc nào đó. Ví dụ [thuật toán tính giá trị biểu thức](https://labuladong.online/algo/data-structure/implement-calculator/) bài trước viết là thuật toán level khó, nhưng nếu dùng hàm `exec`内置 của Python, trực tiếp就能算 ra đáp án.

Cái này ở笔试里肯定 rất占便宜, vì trước說 rồi, ta cần kết quả, không ai quan tâm bạn得到 kết quả thế nào.






## Phân tầng code解法

Phân tầng code应该算 thói quen比较 tốt, có thể tăng tốc viết code và giảm khó debug.

Đơn giản nói là, đừng viết mọi code trong hàm `main`,套路 tôi一直 dùng là, hàm `main`负责 nhận dữ liệu, thêm một hàm `solution`负责统一 xử dữ liệu và output đáp án, rồi dùng một hàm như `backtrack` xử logic thuật toán cụ thể.

Lấy ví dụ, ví dụ một đề, tôi quyết dùng quy hoạch động có memo giải, cấu trúc code đại khái thế này:




```java
public class Main {
    public static void main(String[] args) {
        Scanner scanner = new Scanner(System.in);
        // 主要负责接收数据 -> Chủ yếu nhận dữ liệu
        int N = scanner.nextInt();
        int[][] orders = new int[N][2];
        for (int i = 0; i < N; i++) {
            orders[i][0] = scanner.nextInt();
            orders[i][1] = scanner.nextInt();
        }
        // 委托 solution 进行求解 -> Ủy cho solution giải
        solution(orders);
    }

    static void solution(int[][] orders) {
        // 排除一些基本的边界情况 -> Loại vài case biên cơ bản
        if (orders.length == 0) {
            System.out.println("None");
            return;
        }
        // 委托 dp 函数执行具体的算法逻辑 -> Ủy hàm dp chạy logic thuật toán cụ thể
        int res = dp(orders, 0);
        // 负责输出结果 -> Xuất kết quả
        System.out.println(res);
    }

    // 备忘录 -> Memo
    static HashMap<String, Integer> memo = new HashMap<>();
    static int dp(int[][] orders, int start) {
        // 具体的算法逻辑 -> Logic thuật toán cụ thể
    }
}
```


Bạn xem phân tầng vậy có rõ không, mỗi hàm đều có nhiệm vụ主要负责, chỗ nào出问题, bạn cũng dễ debug.

倒不是 nói phải viết code多规范, còn约束 như `private` miễn cũng無妨, biến đặt tên pinyin cũng OK, mấu chốt là đừng viết thẳng mọi code vào hàm `main`, thật loạn, không lỗi cũng罢, một khi lỗi,估计 tốn công debug, không tìm ra vấn đề loạn trận, đó là要尽量 tránh.

## Debug thuật toán thế nào

Lỗi code không tránh được, đôi khi cả思路都错, đôi khi là vấn đề chi tiết, ví dụ `i` và `j` viết ngược, vấn đề này排查 sao?

Tôi nghĩ bài thuật toán一般肯定 không khó排查, mắt thường check应该都没 vấn đề, cùng lắm `print` vài giá trị biến mấu chốt,总能 phát hiện vấn đề.

**比较让人头疼应该是排查 vấn đề thuật toán đệ quy**.

Nếu không có kinh nghiệm nhất định, quá trình hàm đệ quy rất khó được hiểu đúng, nên ở đây就重点讲 debug thuật toán đệ quy hiệu quả.

Có bạn có thể nói, copy thuật toán vào IDE, rồi打断点 đi từng bước chẳng phải được sao?

Cách này肯定 được, nhưng bài trước nhiều lần nói, hàm đệ quy tốt nhất hiểu từ góc toàn cục, chứ đừng nhảy vào chi tiết cụ thể.

Nếu bạn với đệ quy chưa đủ quen, không có视角 toàn cục, cách打断点 từng bước này cũng dễ绕 người vào.

**建议 của tôi là in thẳng giá trị mấu chốt trong hàm đệ quy,配合 thụt lề, trực quan quan sát tình hình chạy hàm đệ quy**.

Nâng hiệu suất debug ta nhất là thụt lề, ngoài hàm解法, ta định nghĩa mới một hàm `printIndent` và một biến toàn cục `count`:




```java
// 全局变量，记录递归函数的递归层数 -> Biến toàn cục, ghi số tầng đệ quy của hàm đệ quy
int count = 0;

// 输入 n，打印 n 个 tab 缩进 -> Nhập n, in n thụt tab
void printIndent(int n) {
    for (int i = 0; i < n; i++) {
        printf("   ");
    }
}
```


Tiếp theo,套路 tới:

**Ở đầu hàm đệ quy, gọi `printIndent(count++)` và in biến mấu chốt; rồi trước mọi câu `return` gọi `printIndent(--count)` và in返回值**.

Lấy ví dụ cụ thể, ví dụ bài trước [quy hoạch động trong game Fallout](https://labuladong.online/algo/dynamic-programming/freedom-trail/) implement một hàm `dp` đệ quy, cấu trúc đại khái như sau:




```java
int dp(String ring, int i, String key, int j) {
    // base case
    if (j == key.length()) {
        return 0;
    }
    
    // 状态转移 -> Chuyển trạng thái
    for (int k : charToIndex.get(key.charAt(j))) {
        int subProblem = dp(ring, k, key, j + 1);
    }
    
    return res;
}
```


Hàm `dp` đệ quy này sau khi tôi debug, thành thế này:




```java
int count = 0;
void printIndent(int n) {
    for (int i = 0; i < n; i++) {
        System.out.print("   ");
    }
}

int dp(String ring, int i, String key, int j) {
    // printIndent(count++);
    // printf("i = %d, j = %d\n", i, j);
    
    if (j == key.length()) {
        // printIndent(--count);
        // printf("return 0\n");
        return 0;
    }
    

    for (int k : charToIndex.get(key.charAt(j))) {
        int subProblem = dp(ring, k, key, j + 1);
    }
    
    // printIndent(--count);
    // printf("return %d\n", res);

}
```


**Chính là thêm vài code in ở đầu hàm và chỗ tương ứng mọi câu `return`**.

Như vậy, qua so thụt tương ứng就能 biết mỗi lần đệ quy giá trị tham số mấu chốt `i, j`, cùng mỗi lần gọi đệ quy trả kết quả bao nhiêu.

**Quan trọng nhất là, có thể trực quan thấy quá trình đệ quy, bạn có phát hiện đây chính là một cây đệ quy**?

![](https://labuladong.online/algo/images/algo-debug-tech/2.jpg)

Bài trước [chi tiết套路 quy hoạch động](https://labuladong.online/algo/essential-technique/dynamic-programming-framework/) nói, hiểu hàm đệ quy quan trọng nhất chính là vẽ cây đệ quy, in vậy,连 cây đệ quy cũng không cần tự vẽ, mà còn thấy rõ返回值 mỗi lần đệ quy.

**Có thể nói, đây là技巧 nhỏ nâng 「cảm giác hạnh phúc」 khi刷题 nhất, hiệu quả hơn打断点 IDE**.

Tôi ở panel trực quan hỗ trợ thẳng chức năng này, giá trị in trong hàm đệ quy sẽ tự thêm thụt lề, cụ thể xem [hướng dẫn dùng panel trực quan](https://labuladong.online/algo/intro/visualize/).






## Chiến lược ôn trước thi

Trước thi đừng死磕 với một bài thuật toán nào, không划算.

Nên xem càng nhiều đề đủ loại càng tốt, nghĩ năm phút, nghĩ không ra解法 thì xem thẳng đáp án người khác. Hiểu思路 là được, thậm chí tự viết một lần cũng không cần, vì比较 tốn thời gian.

Lúc笔试怕 nhất là không có思路, nên把 đủ loại đề都过目 một chút,起码 trong lòng không慌, chỉ cần có思路, trung bình một đề hai ba mươi phút搞定 vẫn không khó.

Trước不是說么, không có vấn đề gì暴力穷举 không giải được, dùng thẳng [套路 backtrack](https://labuladong.online/algo/essential-technique/backtrack-framework/)硬上, cùng lắm thêm memo, chẳng phải thành [套路 quy hoạch động](https://labuladong.online/algo/essential-technique/dynamic-programming-framework/) sao, cùng lắm đề này tôi không làm么,暴力 qua 60% case cũng挺 OK.

Không nói nhiều,套路 thứ này, nói来 đơn giản,一点就透, nhưng vấn đề là không点就不透. Bài này tôi giới thiệu đơn giản vài技巧 thuật toán笔试, các bạn好好品味~
